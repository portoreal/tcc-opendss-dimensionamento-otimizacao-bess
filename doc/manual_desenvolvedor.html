TCC OpenDSS — Manual do Desenvolvedor

Guia de engenharia para quem vai alterar a ferramenta: arquitetura de processos, contratos entre módulos, invariantes físicas e computacionais, e as armadilhas medidas do motor dss-python. Pressupõe que você já sabe operar o software — o manual do usuário cobre isso.

Repositório: https://github.com/portoreal/tcc-opendss-dimensionamento-otimizacao-bess · Manual irmão: Manual do Usuário · Motor: dss-python 0.15.7

1Arquitetura de Processos

A ferramenta não é um processo único. É uma árvore de processos independentes ligados por linha de comando e sistema de arquivos. Entender isso resolve de antemão a maior parte dos bugs de "funciona na minha máquina": se algo não importa, não converge ou não aparece na tela, a primeira pergunta é em qual processo estou.

1

tcc_opendss.bat

Ponto de entrada. Fica no nível da pasta tcc_opendss (o mesmo nível de venv/ e bibliotecas/). Ativa o venv e delega.

2

verificar_dependencias.py

Processo de console. Confere os pacotes exigidos e instala os faltantes dentro do venv. Falha aqui é falha de ambiente, não de aplicação.

3

bibliotecas/debugger.py

Janela PySide6 com os 11 checks do projeto. Ao concluir com sucesso, lança o menu tcc_opendss.py via subprocess e encerra o próprio processo. Se o usuário fechar a janela sem concluir, encerra sem lançar nada.

4

tcc_opendss.py (menu PySide6)

Orquestrador visual. A partir daqui, cada módulo de interface roda em processo próprio — nenhum diálogo de domínio compartilha o loop de eventos do menu.

O contrato de subprocesso (congelado)

Todo módulo de interface é invocado exatamente assim:

subprocess.Popen(
    [sys.executable, "-m", "bibliotecas.<modulo>", "--projeto", <caminho_raiz>],
    cwd=<raiz>,
)
  • sys.executable — nunca um "python" literal. O venv relocável garante que o interpretador correto é sempre o mesmo do menu.
  • -m bibliotecas.<modulo> — a rota válida é sempre a forma de módulo. Rodar python bibliotecas/x.py diretamente falha por import relativo: o arquivo deixa de ser parte do pacote bibliotecas e os from .modelo_rede import ... estouram.
  • --projeto <caminho_raiz> — obrigatório, exigido pelo argparse de cada lancador. Sem ele o processo aborta na inicialização. Um módulo que aceite ausência de --projeto quebrou o contrato.
  • cwd=<raiz> — o diretório de trabalho é a raiz do projeto. Caminhos relativos no código contam com isso; mudá-lo muda a semântica de leitura de rede.json.
Correção de bug / contrato congelado

Quando estiver depurando um módulo, não "conserte" o import relativo transformando-o em import absoluto para poder rodar o arquivo direto. Isso quebra o pacote para todos os outros processos. A depuração correta é python -m bibliotecas.x --projeto . a partir da raiz.

Códigos de saída do debugger

Canal de retorno do estágio de verificação
CódigoSignificadoConsequência
0 Os 11 checks concluíram com sucesso tcc_opendss.py é lançado por subprocesso; o debugger encerra
1 Janela fechada sem concluir os checks Nada é lançado; o processo termina

Esse par de códigos é consumido pelo .bat e pelo launcher. Qualquer novo código de saída introduzido no debugger precisa ser tratado nos dois lugares — ou tratado como falha.

Transparência técnica — escopo deste fluxo

A cadeia .bat → verificar_dependencias.py → debugger → menu descrita acima é o fluxo do código-fonte (desenvolvimento). No executável distribuído ao usuário final, a mesma cadeia roda embutida no pacote: o interpretador e as dependências já vêm dentro do .exe, e a janela de integridade (11 checks) e o menu continuam existindo como estágios internos. Ver Empacotamento e distribuição.

2.1 Fundação

projeto.py

Modelo do projeto em disco: onde cada artefato mora e como se abre um projeto.

  • Dataclass Projeto — o único objeto do sistema que conhece o layout de pastas.
  • garantir_estrutura() — cria as pastas esperadas de forma idempotente. Qualquer módulo pode chamá-la sem risco.
  • abrir_projeto_por_caminho() / abrir_projeto_por_nome() — as duas entradas do diálogo de seleção.
  • Caminhos padronizados: nunca concatene strings de caminho fora daqui; a fonte da verdade do layout é este módulo.

modelo_rede.py

Estrutura de dados da rede elétrica, serializada como rede.json.

  • RedeEletrica contém Barra, ElementoRamo, ElementoDerivacao e CurvaXY.
  • carregar_json() / salvar_json() — toda a persistência da topologia passa por aqui.
  • rede.json é a fonte da verdade. Artefatos derivados (scripts .dss, dumps, exports) são descartáveis e regeneráveis.

modelo_rede.py · medidor de energia

O EnergyMeter do OpenDSS é uma derivação no modelo, com a mesma identidade das demais.

  • Posição padrão. sugerir_medidor_padrao() devolve o primeiro ramo que toca a barra da fonte — a entrada principal de energia, que é onde a concessionária mede de fato. É sugestão, não imposição: o usuário troca o elemento monitorado quando quiser.
  • resolver_alvo_medidor(elemento, terminal) ancora o ícone na barra correta do ramo; reatribuir_medidores() reescreve a referência quando o ramo é renomeado ou muda de tipo.
  • limpar_medidores_orfaos() apaga o medidor cujo elemento monitorado sumiu. Medidor órfão não é objeto válido — o exportador recusa com ValueError nomeado em vez de emitir um .dss que só falha no motor.
  • limite medido no motor O OpenDSS recusa EnergyMeter apontando para Vsource ou Circuit (“not a Power Delivery element”). O alvo válido é ramo: Line, Switch, Transformer.
  • Exportação. Arquivo próprio medidores.dss (New EnergyMeter.X element=<ramo> terminal=<n>), redirecionado por último em ORDEM_REDIRECT: o elemento monitorado precisa existir antes, e o meter reorganiza as zonas do circuito ao ser definido.

dss_engine.py

Wrapper fino sobre o dss-python: única porta de entrada do motor no sistema.

  • invariante UM COMANDO POR ATRIBUIÇÃO em Text.Command. Bloco multi-linha levanta erro #301. Ver Achados do Motor.
  • Compilação sempre via Compile de arquivo — o motor recebe um .dss em disco, não uma string.
  • motor.Circuit não existe; use motor.ActiveCircuit.
  • Quem precisar de comportamento novo do motor estende este módulo — não chama dss direto de um módulo de camada superior.

ui_win11.py

Camada visual Fluent compartilhada por todo o sistema.

  • Paleta Fluent com accent #004587 (o mesmo desta documentação).
  • Tema claro/escuro lido do registro do Windows (winreg) — não há seletor manual.
  • Diálogos frameless: título e sombra próprios. Nunca assuma a barra de título nativa.

dialogos.py · ui_helpers.py · selecionar_projeto_ui.py

Utilitários de UI: diálogos padronizados, helpers de layout, seleção de projeto.

  • Concentram as mensagens de erro/confirmação do sistema — não escreva QMessageBox ad hoc.
  • selecionar_projeto_ui.py é o produtor do --projeto que circula entre processos.

debugger.py 11 checks

Verificação de integridade do projeto antes de liberar o menu.

  • montar_checks_projeto() — constrói a lista de verificações.
  • iniciar_debugger_projeto(...) -> int — retorna o código de saída (0 = concluiu, 1 = fechado sem concluir).
  • Adicionar um check exige atualizar a contagem exibida e garantir que o ambiente de CI/teste não trave nele.

2.2 Modelagem

editor_rede.py · editor_ui.py

Editor gráfico da RedeEletrica e sua casca Qt.

  • Desenho em QGraphicsScene com barras e derivações arrastáveis; a posição da barra é dado persistido, não decoração.
  • Árvore de elementos em QTreeWidget usando Qt.UserRole para carregar o índice/identidade do elemento — nunca use o texto do nó como chave.
  • armadilha Campos opcionais em CAMPOS_RAMO_PARAMS: c1/c0 em Line, loadloss/noloadloss em Transformer. A chave do dict é SEM % ("loadloss"), mas o comando emitido leva COM % (%loadloss=). Misturar os dois produz comando silenciosamente ignorado.

editor_ui.py · canvas de visualização

Zoom, pan, janela de zoom e o arraste que não rompe a topologia na tela.

  • _CanvasRede (QGraphicsView) concentra a navegação: zoom na roda ancorado no cursor, entre 0,1× e 10×; pan arrastando o fundo vazio ou com o botão do meio; modo “janela de zoom” com rubber band e Esc para sair.
  • _DerivacaoItem é arrastável — o medidor incluído. O arraste grava em _posicoes_derivacoes, que é transitório: não vai para o rede.json, exatamente como já acontecia com o arraste de barras.
  • armadilha Não chame redesenhar() durante o arraste. Reconstruir a cena destrói o item que está sob o mouse e o arraste morre no meio. O caminho correto é o que o código faz: redesenhar() registra _dependencias_por_barra (linhas de ramo, ligações do leque, rótulos) e _atualizar_geometria_barra() aplica a geometria nova ao vivo.
  • O alternador “Mostrar rótulos” esconde rótulos de ramos e derivações e mantém os de barra. Diagrama denso deixa de virar muro de texto sem esconder a identidade dos nós.
Uso na prática: Manual do Usuário, seção 4.1 Editor de Rede

layout_automatico.py

Posicionamento automático das barras no diagrama.

  • Distribuição hierárquica em camadas (técnica de Sugiyama simplificada): atribui nível a cada barra seguindo a topologia e ordena dentro do nível.
  • Gera apenas coordenadas; não altera topologia, parâmetros ou identidade dos elementos.
  • Rodar duas vezes deve ser estável — instabilidade aqui vira "diagrama dançando" a cada reabertura.

exportador_dss.py

Tradutor rede.json → scripts .dss consumíveis pelo OpenDSS.

  • Emite Line, Transformer, Load, Storage, Capacitor, EnergyMeter e as curvas do dia via dia_curvas_padrao.
  • unidades _fmt_line normaliza tudo para km: length convertido e impedâncias levadas a ohm/km, emitindo units=km. A tabela FATOR_PARA_KM é a fonte da verdade — mi = 1,609344; kft = 0,3048; ft = 0,0003048; m = 0,001; cm = 0,00001; in = 0,0000254; unidade ausente conta como km. Ramo com linecode referenciado passa sem conversão — a impedância já está na unidade do código.
  • A motivação é medida, não estética: no binding, km/mi/sem-unidade dão o mesmo resultado e ft não é confiável. Normalizar elimina a ambiguidade comprimento × impedância que produzia linha 3.280× mais longa sem nenhum erro na tela.
  • invariante Estudos exportam para uma pasta TEMPORÁRIA. rede.json nunca é alterado por uma exportação de estudo — se um estudo seu modificou rede.json, isso é bug.

curvas_padrao.py

Curvas de carga e de geração, hora a hora, em percentual.

  • 7 curvas de carga (uma por dia da semana) e 7 sinos de geração fotovoltaica.
  • Valores em percentual, não em kW — a conversão para potência depende do elemento que consome a curva.

curva_editor_ui.py · curvas_semanais_ui.py

Edição de curvas na matriz 7 dias × 24 h.

  • Conversão percentual ↔ potência em tempo real — ao editar um lado, o outro é recalculado; nunca armazene os dois como fonte da verdade.
  • A matriz é sempre completa (7 × 24). Curva parcial é erro de entrada, não caso especial.

2.3 Dimensionamento

dimensionamento_regras.py puro

Núcleo normativo do dimensionamento. Funções puras, SEM toolkit — não importa Qt, não importa motor, não faz I/O.

  • dimensionar_linha — corrente I = S / (√3 · V); queda √3 · I · (R·cosφ + X·senφ) / V; escolhe o menor condutor que satisfaz ampacidade e queda; assume r0/x0 = 3 × r1/x1.
  • dimensionar_transformador — S = P / cosφ, aplica margem, escolhe a menor potência padrão; XHL atribuído por faixa de 3,5–6,5%.
  • dimensionar_storage — kWh = P · t / (DoD · η).
  • dimensionar_capacitor — Q = P · (tanφa − tanφd).
  • dimensionar_reator_indutivo — resultado arredondado a múltiplo de 50 kvar.
  • dimensionar_fotovoltaico — kWp = consumo / (30 · HSP · PR).
  • dimensionar_gerador — fator de demanda + margem.
  • Catálogos: CATALOGO_CONDUTORES, POTENCIAS_PADRAO_TRAFO_KVA, POTENCIAS_PADRAO_GERADOR_KVA.
  • contrato de retorno Toda função retorna {"parametros": <dict no formato OpenDSS>, "memoria_calculo": <texto auditável>}. A memoria_calculo não é comentário: é o que permite auditar a escolha. Devolver só parametros quebra o memorial.

dimensionamento_ui.py · dimensionamento_lancador.py

Interface do dimensionamento e seu ponto de entrada com --projeto.

  • O lancador é o módulo executável (-m bibliotecas.dimensionamento_lancador); a ui é importada por ele.
  • A UI apenas coleta entradas e renderiza o retorno de dimensionamento_regras — cálculo na UI é violação de camada.
Uso na prática: Manual do Usuário, seção 4.2 Dimensionamento

2.4 Análise

estudo_afundamento.py

Motor reutilizável de afundamento de tensão por falta.

  • MotorReutilizavel — reaproveita a instância do motor entre cenários, evitando recompilar a rede a cada falta.
  • rodar_estudo — falta barra a barra, trifásica e monofásica, com r_falta_solida = 0,05 Ω.
  • _classificar_sag — janela de sag de 0,1 a 0,9 pu, excluindo a barra faltosa da classificação (a própria barra em falta não é "vítima").
  • semântica de colapso Cenário que não convergiu recebe sentinela pu = [limite_inferior] = 0,1 em todas as barras exceto a faltosa. Divergência é penalizada, nunca creditada. Sem isso, um caso divergente apareceria como "sag profundíssimo" e seria escolhido pela otimização como o melhor candidato.
  • O campo "convergiu" em detalhe_por_falta é o que separa medição de penalidade — consumidores precisam checá-lo.
  • _nome_base_barra normaliza toda chave de barra para minúsculas. invariante Nunca compare nomes de barra sem normalizar — "B610" e "b610" são a mesma barra e chaves distintas.
  • VMINPU_STORAGE_PADRAO = 0,05 no Storage, para manter a injeção nominal na faixa de sag (o default do motor é 0,9 — ver Achados).

reativo_analise.py

Avaliação de fator de potência e compensação reativa.

  • Compara o FP no ponto de conexão com o limite de 0,92 exigido pelo PRODIST.
  • Dimensiona capacitor ou reator conforme o desvio (capacitivo vs indutivo) — reusando dimensionamento_regras, não reimplementando a fórmula.

memorial_calculo_afundamento.py · memorial_calculo_economia.py

Memoriais textuais auditáveis.

  • Transformam resultados numéricos em texto com as premissas explícitas.
  • Um memorial que não permite refazer a conta à mão é um memorial incompleto.

2.5 Otimização

otimizacao_bess.py orquestrador

executar_estudo_completo — a espinha dorsal do TCC.

  • Sequência: caso base → varredura exaustiva barra × catálogo (sag binário + severidade contínua + economia por candidato) → MILP → verificação conjunta → reativo → economia completa → análise semanal (passo 4c) → memoriais.
  • Assinatura headless: executar_estudo_completo(caminho_master, ..., rede=, pasta_curvas=). Passando a rede e a pasta de curvas, a economia semanal entra no resultado; sem elas o estudo roda igual e o campo fica None.
  • ponto crítico Na verificação conjunta, o benefício REAL medido substitui a estimativa-soma dos benefícios individuais. Somar benefícios de candidatos selecionados superestima grosseiramente — dois BESS vizinhos não somam redução de sag.
  • _profundidades_por_barra — profundidade da barra = max(0, V_sup − min(pu)), com média entre cenários.
  • Escalas físicas usadas para normalizar o objetivo MILP: σ_Q = (V_sup − V_inf) · n_sag e σ_E = spread · D_max · h_p · d · 12.
  • armadilha O motor muda o CWD do processo ao compilar. Salve qualquer artefato com caminho absoluto calculado antes do estudo — caminho relativo resolvido depois aponta para o diretório errado.
Uso na prática: Manual do Usuário, seção 4.3 Otimização de BESS

otimizacao_milp.py PuLP + CBC

Programa inteiro misto de seleção de portes por barra.

  • Variável yi binária; objetivo w_Q · Si/σ_Q + w_E · Ei/σ_E − w_C · Ci/σ_C.
  • Restrições: ≤ 1 porte por barra, ≤ max_unidades, orçamento opcional.
  • não-vacuidade A seleção vazia tem objetivo 0 e perde para qualquer candidato com mérito líquido positivo. É isso que impede o solver de "não fazer nada" e chamar de ótimo.
  • exceção conhecida Com pesos patológicos w_C ≥ máx(w_Q, w_E), a seleção vazia volta a poder vencer — o custo domina qualquer benefício. Não é bug: é o modelo respondendo ao peso dado.
  • fallback Sem escala física disponível, usa o máximo observado (comportamento retrocompatível), que é sujeito a amplificação de outlier: um único valor extremo comprime todos os demais e distorce a ordenação.
Uso na prática: Manual do Usuário, seção 4.3 Otimização de BESS

otimizacao_ui.py · otimizacao_lancador.py

Interface do estudo de otimização.

  • ConfiguracaoEstudoDialog → execução em thread + fila + QTimer. O cálculo nunca roda no thread da UI; a fila é drenada por QTimer.
  • ResultadosDialog com abas e barra de botões: ESP32, ROI/DRE, Aplicar ao Projeto.
  • "Aplicar ao Projeto" é a única ação que escreve de volta no projeto — e é explícita do usuário.
Uso na prática: Manual do Usuário, seção 4.3 Otimização de BESS

otimizacao_exportar_roi.py

Relatório ROI/DRE em HTML standalone.

  • DRE sem O&M, com nota de transparência declarando a omissão.
  • Projeção de min(max(ceil(payback) + 2, 10), 25) anos.
  • 6 gráficos matplotlib com backend Agg, embutidos em base64 — o HTML não depende de CDN nem de arquivos irmãos. Os dois últimos vêm da análise semanal: economia dia a dia (R$/dia, barras verdes contra vermelhas) e composição percentual das fontes por dia (rede, FV e BESS empilhados até 100%).
  • Formatação pt-BR com helpers próprios, sem module locale.
  • INCENTIVOS_PADRAO editável; valores padrão são didáticos, não contratuais.
  • armadilha float()/int()/bool() em TUDO que sai do motor: np.float64 vaza para o template e o json.dumps estoura com not JSON serializable.
Uso na prática: Manual do Usuário, seção 4.4 Relatório ROI / DRE

2.6 Economia

economia_energia.py

Simulação econômica horária (QSTS) e cálculo de payback.

  • QSTS de 24 h com passo de 1 h.
  • Despacho: na ponta → discharging se SoC > 0,2; fora da ponta → charging se SoC < 0,95; caso contrário idling.
  • invariante NUNCA escreva kW manualmente. Só o State é escrito via texto, com %Charge=100 / %Discharge=100. Potência imposta à mão conflita com o controle interno do Storage e produz resultado que não corresponde a nenhum equipamento real.
  • calibração de sinal _calibrar_sinal_importacao roda um micro-circuito de importação conhecida para descobrir o sinal de Circuit.TotalPower[0]. A convenção de sinal é da instância do motor, não do circuito — não a presuma.
  • Economia = deslocamento na ponta − carga extra fora da ponta. Payback = CAPEX / economia_anual.
  • Emite alertas de honestidade do dado quando a premissa é frágil (ex.: tarifa sem tributos, curva genérica).
Uso na prática: Manual do Usuário, seção 4.5 Economia de Energia

economia_energia.py · análise semanal

analisar_economia_semanal(rede, pasta_curvas, dia_padrao, bess_list, tarifa, ...) — sete dias × 24 h, não o dia representativo.

  • Por dia: cópia profunda da rede com rebind das curvas daquele dia — a curva do projeto tem prioridade; sem vínculo, a exportação injeta a curva padrão do dia. Cada dia exporta para pasta temporária própria e roda duas passadas de despacho (base e com BESS).
  • Contrato devolvido: {"dias", "economia_diaria_brl", "custo_base_diario_brl", "custo_sistema_diario_brl", "energia_rede_kwh", "energia_fv_kwh", "energia_bess_kwh", "economia_semanal_brl", "avisos"}.
  • Energia por fonte: rede = soma das kw_comprada do perfil; FV = geração consumida, já descontada a exportação; BESS = descarga. Carregamento não entra como fonte — consumir a própria bateria para recarregá-la não é geração.
  • degradação Falha em um dia zera aquele dia e registra aviso; a semana inteira não se perde por causa de um sábado. Só ausência total vira None.
  • Gancho no estudo. executar_estudo_completo ganhou os parâmetros rede= e pasta_curvas=; com tarifa e rede presentes, o passo 4c anexa resultado["economia_semanal"] (e avisos_semanais quando falha).

tarifas_energia.py

Tarifas e estrutura tarifária.

  • Dataclass TarifaEnergia; catálogo CELESC REH 3.602/2026.
  • Valores sem tributos por decisão de projeto — informe isso em qualquer relatório econômico.

catalogo_bess.py

Portes comerciais de BESS usados na varredura.

  • 8 portes, de 5 kW / 10 kWh a 1000 kW / 2000 kWh.
  • Custos referenciais didáticos — não são cotação de mercado.

2.8 Hardware

exportador_arduino.py · exportador_esp32.py

Parametrização de sketches pré-existentes para a maquete física.

  • não é gerador de código Estes módulos parametrizam sketches pré-prontos e fixos em hardware/. Eles não sintetizam código.

3Achados do Motor dss-python 0.15.7

Cada item abaixo foi encontrado depurando comportamento divergente, não lendo documentação. A consequência importa mais que o sintoma: é ela que decide se o seu código está errado ou apenas parece.

Armadilhas medidas e sua consequência
#ArmadilhaConsequência
1 Text.Command levanta DSSException no erro Um comando inválido no meio de uma sequência interrompe a sequência — trate por comando, não em bloco.
2 NÃO aceita bloco multi-linha numa atribuição (erro #301) Deve haver um comando por atribuição; strings com \n são rejeitadas inteiras.
3 motor.Circuit não existe Use motor.ActiveCircuit; o atributo inexistente falha em tempo de execução, não de import.
4 BusList não materializa durante o Compile SetBusXY inline falha silenciosamente; emita a posição pós-Compile, com a lista já povoada.
5 Convenção de sinal de TotalPower é da instância Calibre o sinal em tempo de execução; assumir que importação é positiva produz economia com o sinal invertido.
6 Hierarquia de R série em trafo de 2 enrolamentos %r por enrolamento explícito (inclusive 0) prevalece sobre %LoadLoss — declarar %r=0 zera a resistência série mesmo havendo %LoadLoss.
7 Sem %r, a R série vem do %LoadLoss O default efetivo medido é ≈0,4%, não os 1,5556% que a literatura sugere — perdas do trafo ficam subestimadas se você confiar no valor de catálogo.
8 %noloadloss isolado desloca o ponto de operação Preencha sempre o PAR: %loadloss e %noloadloss; c1 e c0. Meio par deforma a tensão de operação.
9 Shunt C default de linha: C1=3,4 / C0=1,6 nF/km quando não declarado Linhas sem capacitância explícita já têm reativo capacitivo; declarar 0 muda o perfil de tensão em relação ao default do motor.
10 Storage default Vminpu=0,9 Degrada a injeção exatamente na faixa de sag; o projeto usa 0,05 (VMINPU_STORAGE_PADRAO), senão o BESS "desaparece" no momento em que deveria ajudar.
11 ILines.RMatrix não existe — o atributo é Rmatrix Acesso ao nome errado devolve None sem levantar erro; o código cai no fallback e usa impedância padrão em toda a rede.
12 ILines.Units, lido como número, retorna sempre 0 A unidade legível só existe na consulta de texto do elemento. Confiar no campo numérico faz você “confirmar” uma unidade que não foi lida.
13 Circuit.TotalPower[0] devolve kW nesta versão Carga de 100 kW lida como −100,83. Dividir por 1000 “para converter” derruba a medição mil vezes — a calibração de sinal continua obrigatória, a conversão de escala não.
14 O motor altera o CWD do processo ao compilar Caminho relativo resolvido depois do Compile aponta para outro diretório. Calcule caminhos absolutos antes do estudo.
15 Arredondar impedância por-milha em 4 casas zera a resistência Valores da ordem de 1e-4 Ω/mi desaparecem no arredondamento. O round destrutivo foi removido; arredonde só na apresentação, nunca no valor que vai ao motor.
16 EnergyMeter exige elemento de entrega de potência Apontar para Vsource ou Circuit falha com “not a Power Delivery element”. Use Line, Switch ou Transformer.
Atenção — padrão de falha comum

Os itens 4, 5 e 9 têm a mesma assinatura: o motor não reclama. Ele aplica um default e segue. Um estudo que "roda sem erro" e produz número estranho é quase sempre um default não intencional — não uma instabilidade numérica.

Transparência técnica — escopo dos achados

Estes achados são da versão 0.15.7. Atualizar o dss-python exige re-verificar os 16 itens, priorizando 4, 5, 6, 7, 10, 13 e 15, cujos efeitos numéricos são grandes o bastante para invalidar comparações com resultados anteriores.

Contexto de uso

Vários destes defaults se manifestam ao usuário como número estranho, não como erro — a falha chega na tela, não no log. Quando o usuário relatar resultado implausível num cenário que "roda sem erro", comece por aqui. Manual do Usuário, seção 6 Solução de Problemas.

4Invariantes e Convenções de Código

Idioma e forma

  • Nomes em português — módulos, funções, variáveis e chaves de dicionário. Não traduza nem misture.
  • Arquivos entregues COMPLETOS. Não entregue diff parcial nem "resto igual" — o arquivo é a unidade de entrega.
  • armadilha real UTF-8 sempre. Acento dentro de docstring já causou SyntaxError em ambiente com codificação default diferente. Se o arquivo precisa ser ASCII-safe para alguma ferramenta, o acento vai em comentário e o texto visível em escape — mas a regra é UTF-8 explícito.
  • Sem pandas. As séries do projeto são listas e numpy; introduzir pandas adiciona dependência e peso de startup sem ganho.
  • Formatação pt-BR sem module locale: vírgula decimal e ponto de milhar vêm de helpers próprios. locale.setlocale é global ao processo e contamina os outros módulos.

Blocos de transparência

Todo ponto onde o código supõe, descobre ou corrige algo precisa de um bloco correspondente:

Transparência técnica

Para suposições: o que se assume, por quê, e o efeito se a suposição for falsa.

Atenção

Para achados de comportamento inesperado do motor, do hardware ou de dado de entrada.

Esses blocos existem no código, junto da linha afetada. Um deles não substitui o memorial de cálculo; o memorial audita a engenharia, o bloco audita a implementação.

5Testes Headless

O padrão do projeto é validar sem abrir janela. Isso permite rodar a verificação a cada mudança, não só no fim.

Receita mínima

# cwd = raiz do projeto (o mesmo nível de venv/ e bibliotecas/)
venv/Scripts/python.exe -m py_compile bibliotecas/<modulo>.py
venv/Scripts/python.exe -m bibliotecas.<lancador> --projeto .   # se aplicável
  • venv/Scripts/python.exe, nunca o Python do sistema — o venv carrega as versões certas de dss-python, PySide6 e PuLP.
  • cwd na raiz. Os caminhos relativos do projeto dependem disso.

Orçamento de tempo

Um estudo completo de otimização roda em ~5–8 s com 48 candidatos. É rápido o bastante para rodar a cada edição relevante — e qualquer mudança que leve o tempo para muito além do orçamento, introduziu recompilação desnecessária ou perda do MotorReutilizavel.

Regressão numérica

  • Tolerância 1e-9 ao comparar contra as referências.
  • Referências em projetos/teste/dump_estudo_otimizacao.json.
  • Comparação por caminho de chave, não por igualdade de dicionário inteiro — assim a mensagem de falha aponta o campo divergente.

Smoke test de UI

QT_QPA_PLATFORM=offscreen venv/Scripts/python.exe -m bibliotecas.<lancador> --projeto .

QT_QPA_PLATFORM=offscreen instancia widgets sem display. Cobre import, construção de diálogo e fiação de sinais — não cobre layout visual nem interação real. Para módulos que desenham PNG, garanta também MPLBACKEND=Agg.

Ordem de validação recomendada

py_compile → import do módulo → smoke offscreen → estudo completo comparado ao dump. Um passo por vez: quando algo quebra, você sabe qual degrau cedeu.

Atenção

py_compile antes de qualquer entrega. Acento em docstring e import relativo quebrado só aparecem na compilação, não na revisão visual do diff.

Contexto de uso

Teste headless cobre contrato, não experiência. O que escapa daqui — mensagem confusa, projeto inválido, caminho renomeado — aparece para o usuário final como sintoma de tela. Manual do Usuário, seção 6 Solução de Problemas.

6.1 Empacotamento e distribuição

O código-fonte e o artefato entregue ao usuário final são dois modos de execução distintos do mesmo programa. Confundir os dois é a origem da maior parte das dúvidas de suporte.

Os dois modos de execução
ModoArtefatoRequisito no computador do usuário
Distribuído entrega Executável autônomo (*.exe) com interpretador e dependências embutidos Não precisa de Python instalado. Nada de pip, venv ou .bat.
Desenvolvimento código-fonte tcc_opendss.bat → verificar_dependencias.py → debugger.py sobre o venv/ Python 3, venv/ gerado e internet na primeira execução

Modo distribuído

No pacote executável, o interpretador e todas as dependências (dss-python, PySide6, matplotlib, PuLP, openpyxl) viajam dentro do .exe. O usuário final não precisa de Python instalado e não executa nenhuma etapa de instalação de pacotes. A janela de integridade com os 11 checks e o menu principal continuam executando normalmente — eles são estágios internos do pacote, não scripts externos.

Modo de desenvolvimento

A cadeia .bat → verificar_dependencias.py → debugger.py → menu permanece sendo o caminho de desenvolvimento e teste: é onde se roda py_compile, testes headless e smoke offscreen. O detalhamento dos estágios está em Arquitetura de Processos.

Regra de manutenção

Atenção — publicação de versão

Qualquer alteração de dependências em verificar_dependencias.py ou requirements.txt exige regenerar o pacote executável antes de publicar na página de Releases do repositório — https://github.com/portoreal/tcc-opendss-dimensionamento-otimizacao-bess. Versão do código e versão do .exe nunca podem divergir: o usuário não tem como atualizar uma dependência por conta própria.

Transparência técnica — estado do empacotamento

O empacotamento em executável é etapa planejada pelo autor; enquanto o pacote não existir na página de Releases, o modo de execução válido é o código-fonte (.bat), e a documentação do usuário descreve ambos os modos.

7Estudo de Demonstração — IEEE 13 Barras

O projeto projetos/ieee13/ existe para responder uma pergunta que o caso sintético não responde: o método completo funciona num alimentador com desequilíbrio real, regulador e cargas monofásicas espalhadas? Serve também como caso de regressão do conversor.

Como o projeto foi montado

  • Rede convertida pelo conversor canônico — exportar_sistema_como_projeto(), o mesmo caminho que qualquer usuário usa. Nada foi digitado à mão.
  • 16 barras, 15 ramos, 19 derivações. Cargas somando 3.466 kW / 2.102 kvar, com diferença zero contra o arquivo oficial do comitê.
  • FV de 1.000 kWp (PVSystem) na barra 675. É a barra de maior carga e trifásica, condição que evita somar ao caso a discussão sobre conexão monofásica de gerador.
  • O regulador foi colapsado num transformador com boost simétrico kv2 = 4,411333, média dos taps originais (1,0625 / 1,0500 / 1,06875). Perde-se a regulação por fase, mantém-se a elevação média — a alternativa era perder o boost inteiro.

Resultado do estudo

O fator de potência de 0,5622 é consequência direta do FV: em carga leve, o alimentador devolve reativo à fonte. Não é defeito do modelo — é o que o cenário faz com ele.

Limitação declarada — endereçamento de fase

O modelo de dados não guarda a fase de cada elemento. Na conversão, as cargas monofásicas empilham na fase 1, o que desequilibra o caso de forma que o alimentador original não tem. Números medidos: Vmin = 0,8407 pu contra 0,975 do gabarito; perdas de 192,23 kW contra 110,50 kW; erro médio de 8%. Os resultados de otimização acima são internamente consistentes, mas o caso base não reproduz o perfil oficial. Fechar essa lacuna exige um campo de fase no rede.json — mudança de modelo, deliberadamente fora desta versão.
